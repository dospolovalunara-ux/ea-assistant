## 1. Описание продукта

EXECUTIVE AI — защищённое веб-приложение, цифровой офис помощника руководителя. Оно объединяет:
- рабочий и личный календари;
- входящие сообщения;
- задачи и поручения;
- протоколы совещаний;
- корпоративные и личные расходы;
- каталог семейных документов.

**Главный принцип:** AI извлекает информацию, классифицирует её и предлагает действия. Подтверждения человека требуют:
- создание важных записей;
- финансовые изменения;
- экспорт и отправка документов.

## 2. Цели

- Сократить ручной перенос данных между мессенджерами, календарём, таблицами и документами.
- Не допускать забытых встреч, поручений, чеков и сроков действия документов.
- Ускорить подготовку протоколов и реестров расходов.
- Создать единое рабочее пространство с раздельными правами доступа.
- Не хранить пароли и секреты внешних сервисов в приложении и не передавать их AI.

## 3. Принятые решения по неоднозначностям v1.0

| Вопрос | Решение |
|---|---|
| «Не хранить пароли» и при этом нужен вход в приложение | Пароль для входа в само приложение хранится только как bcrypt-хеш, это стандартная практика. Запрет относится к секретам сторонних сервисов: банки, почта, 2FA, recovery codes. Позже вход можно перевести на корпоративный SSO. |
| Статус задачи «просрочена» | В базе не хранится, вычисляется при каждом запросе: срок прошёл, а задача не выполнена и не отменена. Так статус всегда соответствует действительности. |
| Какие задачи видит руководитель | У задачи есть поле `visibility`: `private` (видит только помощник) или `shared` (видит руководитель). Задачи, назначенные на руководителя, видны ему всегда. |
| Чей календарь | Оба календаря, рабочий и личный, принадлежат руководителю. Помощник управляет ими по своим правам. |
| Пересечения встреч | Проверяются по обоим календарям сразу: у руководителя одно время. Черновики и отменённые события не учитываются. Сохранить событие с пересечением можно только после явного подтверждения. |
| Напоминания | В интерфейсе появятся только вместе с фоновым планировщиком, который действительно их отправляет. Без него кнопка была бы фиктивной. |
| Нереализованные модули в меню | Показываются серыми, с пометкой «В разработке», нажать их нельзя. |

## 4. Пользователи

### Помощник — Executive Assistant
Полный рабочий доступ в рамках выданных полномочий:
- календарь, задачи, расходы, документы, протоколы, отчёты;
- журнал действий;
- настройки интеграций (после их появления).

### Руководитель — Executive
- Просматривает свой календарь, согласованные задачи, протоколы и отчёты, а также личные расходы.
- Меняет статус задач, назначенных на него, и комментирует доступные ему задачи.
- Подтверждает и отклоняет предложенные действия (после появления Inbox и AI).
- Не видит личные заметки помощника и административные настройки, если это отдельно не разрешено.

### Технический администратор (опционально)
- Управляет пользователями, конфигурацией и инфраструктуру, читает журнал действий.
- Сама по себе роль **не даёт** доступа к календарю, задачам, финансам и документам.

## 5. Ролевая модель (RBAC)

Права записываются строками вида `модуль.действие`. Роль — это набор прав. Отдельному пользователю можно добавить право точечно (`user_permissions`). Все права проверяются на сервере в каждой функции бизнес-логики. Действует принцип минимально необходимых полномочий.

| Право | Помощник | Руководитель | Тех. админ |
|---|:-:|:-:|:-:|
| `dashboard.view` | ✓ | ✓ | |
| `calendar.read` | ✓ | ✓ | |
| `calendar.write` | ✓ | | |
| `tasks.read_all` (включая `private`) | ✓ | | |
| `tasks.read_shared` | ✓ | ✓ | |
| `tasks.write` | ✓ | | |
| `tasks.update_status_assigned` | ✓ | ✓ | |
| `tasks.comment` | ✓ | ✓ | |
| `audit.read` | ✓ | | ✓ |
| `users.manage` | | | ✓ |

Права для будущих модулей:
- `inbox.*`
- `expenses.corporate.*` и `expenses.personal.*` — отдельно друг от друга
- `documents.*`
- `protocols.*`
- `integrations.manage`

Правила доступа:
- Если запись недоступна, сервер отвечает «не найдено» и не раскрывает, что она существует.
- Каждый отказ в доступе записывается в журнал (`access.denied`).

## 6. Модули продукта

### 6.1 Dashboard — ✅ реализован
Показывает:
- встречи сегодня и на 3 дня вперёд;
- задачи на сегодня, просроченные и ожидающие ответа;
- счётчики по каждому разделу.

Все показатели рассчитываются запросами к базе, AI их не генерирует. Каждый пользователь видит только данные, доступные его роли.

*Добавится позже:* протоколы на проверке, расходы без документов, документы с истекающим сроком, новые входящие, сводка открытых процессов.

### 6.2 Unified Calendar — ✅ основа реализована
Рабочий и личный календари показываются вместе, с фильтрами и цветовым различием (рабочий — синий, личный — зелёный).

**Типы событий:** рабочая встреча, совещание/Zoom, деловой обед, командировка, личное событие, семейное событие, напоминание, занято.

**Поля события:**
- название, тип, календарь;
- начало, окончание, «весь день», часовой пояс;
- место, ссылка на видеоконференцию;
- организатор, участники, повестка;
- источник, важность;
- поля для синхронизации с Google: `external_id`, `external_etag`.

**Статусы:** черновик, ожидает подтверждения, подтверждено, перенесено, отменено, завершено.

**Уже работает:**
- виды «неделя» (сетка по часам; пересекающиеся события встают рядом; красная линия текущего времени) и «список» (14 дней);
- создание, изменение и отмена (событие остаётся в истории со статусом «Отменено»);
- проверка пересечений с явным подтверждением «Всё равно сохранить»;
- история изменений события.

**Проверка ввода на сервере:**
- окончание должно быть позже начала;
- ссылки принимаются только с `http://` или `https://` (защита от XSS);
- на неверные поля возвращаются понятные ошибки.

**Позже:** виды «день» и «месяц», поиск свободных интервалов, синхронизация с Google Calendar, напоминания, утренний брифинг, создание события из текста с помощью AI.

**Правило для AI:** неоднозначные данные не угадываются. AI создаёт черновик и задаёт уточняющий вопрос. До подтверждения событие в календарь не записывается.

Часовой пояс по умолчанию — `Asia/Almaty`. В базе всё хранится в UTC.

### 6.3 Inbox — входящие материалы — ⏳ Sprint 3b
Принимает: текст, голосовую заметку, аудио, фото, PDF, офисный документ, ссылку, вручную пересланное сообщение.

AI предлагает категорию:
- встреча;
- задача/поручение;
- протокол;
- корпоративный расход;
- личный расход;
- чек;
- семейный документ;
- поездка;
- справочная информация;
- неизвестно / нужна ручная обработка.

Хранятся: исходный материал, время поступления, категория, извлечённые поля, уверенность распознавания и статус (`proposed → confirmed | rejected`). Пользователь может исправить результат.

В MVP — только ручная вставка и загрузка. Неофициальные способы чтения WhatsApp не используются, мессенджеры подключаются только официально.

### 6.4 Tasks & поручения — ✅ реализованы
**Поля:**
- название, описание, источник;
- ответственный: пользователь системы или вписанное имя, например «Юридический отдел»;
- постановщик, срок, приоритет, статус, видимость;
- связанное событие;
- комментарии, история изменений.

**Статусы:** новая, в работе, ожидает ответа, на проверке, выполнена, отменена. «Просрочена» вычисляется, а не хранится.

**Приоритеты:** низкий, обычный, высокий, срочный.

**Разделы:** Все открытые, Сегодня, На неделе, Просрочено, Ожидает ответа, Завершено. У каждого есть счётчик. «Сегодня» определяется по местному дню, а не по UTC.

**Уже работает:**
- создание и редактирование;
- быстрая смена статуса;
- комментарии;
- история изменений из журнала действий.

**Позже:**
- напоминания до дедлайна и при просрочке;
- поручения из протоколов, связанные с исходной встречей;
- подтверждение неоднозначных ответственных и сроков.

### 6.5 Meeting Intelligence — протоколы — ⏳ Sprint 5
**Процесс:**
1. Загрузка разрешённого файла или транскрипта.
2. Проверка формата.
3. Распознавание речи в согласованном сервисе.
4. AI готовит черновик протокола.
5. AI извлекает решения, поручения, ответственных и сроки.
6. Помощник проверяет и правит.
7. После подтверждения сохраняется финальная версия, а поручения становятся задачами.

**Структура протокола:** название, дата и время, формат/место, участники, повестка, краткое содержание, решения, поручения, ответственные, сроки, вопросы на уточнение, ссылка на исходник, статус и версии.

**Ограничения:**
- Запрещено выдумывать участников, решения, цитаты, поручения и сроки.
- Неуверенные фрагменты помечаются «требует проверки».
- Черновик нельзя выдавать за утверждённый протокол.
- Экспорт в DOCX и PDF.
- Отправка внешним адресатам — только после явного подтверждения.

### 6.6 Corporate Expenses — корпоративные расходы — ⏳ Sprint 4
Отдельный реестр расходов по корпоративной карте.

**Поля:** дата/время, сумма (`numeric(14,2)`), валюта (по умолчанию KZT), организация, категория, описание, связанное событие, способ оплаты, статус документов, комментарий, вложения.

**Документы:** фискальный чек, QR-подтверждение, товарный чек (если нужен), подтверждение оплаты, другие документы по правилам бухгалтерии.

**Функции:**
- загрузка фото и PDF, OCR;
- привязка к встрече;
- поиск возможных дубликатов;
- чек-лист недостающих документов;
- экспорт в XLSX и PDF;
- комплект документов для бухгалтерии;
- напоминание собрать документы перед деловым обедом.

AI не гарантирует, что авансовый отчёт примут, и не утверждает расходы.

### 6.7 Personal Expenses — личные расходы — ⏳ Sprint 4
Отдельный финансовый контур: отдельные таблицы и отдельные права, данные не смешиваются с корпоративной картой.

**Типы операций:** передача или поступление денег, расход, возврат остатка, корректировка (причина обязательна).

**Функции:**
- баланс по каждой передаче, остаток;
- история операций и категории;
- дневной и месячный отчёт;
- экспорт в XLSX и PDF.

Баланс считается SQL-запросом, не языковой моделью. AI может разобрать текст вроде «обед 4500, кофе 1200», но перед сохранением пользователь подтверждает обе операции.

### 6.8 Family Documents — семейные документы — ⏳ Sprint 5, после согласования ИБ
Защищённый каталог документов руководителя и членов её семьи.

**Категории:** документы руководителя, супруга, детей; семейные свидетельства; недвижимость; автомобили; страхование; доверенности; справки; образование; поездки и визы; прочее.

**Метаданные:** название, категория, владелец, тип, дата выдачи, срок действия, орган выдачи (если разрешено), минимально необходимый номер, ссылка на защищённый файл, дата загрузки, автор, уровень конфиденциальности, права доступа, напоминания, статус.

**Функции:**
- загрузка и скачивание по правам;
- поиск по метаданным, фильтр по владельцу;
- напоминания о сроках;
- версии;
- аудит просмотра, скачивания и изменения.

По умолчанию AI работает только с разрешёнными метаданными. Содержимое персональных документов не передаётся внешней модели без отдельного согласования. Предпочтительны локальный OCR или одобренный корпоративный сервис.

### 6.9 Password Vault — только ссылка на менеджер паролей
- Собственное хранилище паролей не создаётся.
- Пароли, PIN, коды 2FA, recovery codes, ключи, ответы на секретные вопросы и токены не хранятся в базе приложения.
- Допускаются ссылка на запись в утверждённом корпоративном менеджере паролей (с MFA) и несекретная подсказка о владельце учётной записи.
- AI не видит секреты.

### 6.10 Reports — ⏳ после Sprint 4
**Для помощника:** задачи на день; недельная сводка встреч, протоколов и поручений; расходы и недостающие чеки; сроки документов.

**Для руководителя:** расписание, согласованные поручения, протоколы, согласованные финансовые сводки.

**Форматы:** экран, PDF, DOCX, XLSX. Суммы и даты берутся из базы. AI формулирует пояснения, но исходные значения не меняет.

### 6.11 Журнал действий (Audit log) — ✅ реализован
**Что записывается:**
- входы, выходы, неудачные попытки входа, блокировки;
- отказы в доступе;
- создание, изменение и отмена событий;
- создание и изменение задач, смена статусов, комментарии.

**Как устроен:**
- Хранятся пользователь, действие, объект, IP и метаданные.
- В метаданные не попадают пароли, токены и содержимое документов.
- Изменить или удалить запись нельзя: это запрещает триггер на уровне базы.
- Журнал доступен помощнику и техническому администратору.

## 7. Уведомления — ⏳ Sprint 2b
- Часовой пояс — `Asia/Almaty`.
- Встречи — настраиваемые напоминания, например за 60 и 15 минут.
- Задачи — напоминание до дедлайна и при просрочке.
- Утренний брифинг — время задаёт пользователь.
- Деловые встречи — напоминание собрать документы.
- Документы — настраиваемые интервалы до окончания срока, например за 30, 14 и 3 дня.
- Каналы: внутри приложения; email и Telegram — после подключения и согласования.
- В push-уведомлениях на заблокированном экране нет конфиденциальных сведений.

## 8. Поведение AI

AI:
- работает только с данными, доступными текущему пользователю;
- показывает источник каждого извлечённого факта;
- различает факт, вывод и предположение;
- задаёт вопросы при неоднозначности и не выдумывает записи;
- не скрывает ошибки интеграций;
- не изменяет оригиналы документов;
- не выполняет инструкции, встроенные в загруженные файлы, если они пытаются изменить правила или получить доступ к данным;
- журналирует свои предложения и подтверждённые действия.

**Уровни автоматизации:**
- **Suggest** — AI предлагает.
- **Confirm** — AI готовит действие и ждёт подтверждения.
- **Approved automation** — заранее разрешённые низкорисковые действия.

В MVP доступны только Suggest и Confirm.

**Архитектурное правило:** AI не пишет в рабочие таблицы. Он создаёт запись в `ai_extractions`, а запись в рабочей таблице создаёт обычный серверный код после подтверждения человека. Финансовые вычисления делает только программный код. Если AI недоступен, приложение показывает ошибку и даёт продолжить работу вручную.

## 9. Безопасность

### 9.1 Реализовано
| Угроза | Защита |
|---|---|
| Подбор пароля | bcrypt (cost 12). Блокировка после 5 неудачных попыток за 15 минут по email и после 20 — по IP. Одинаковые ответ и время ответа для существующих и несуществующих email. |
| Кража сессии | Случайный токен 256 бит, в базе хранится только его SHA-256-хеш. Cookie `HttpOnly; Secure; SameSite=Lax`, срок 12 часов. При выходе сессия удаляется. |
| Обход ролей | Проверка прав в каждой функции сервиса, автотесты обхода ролей. |
| Доступ к чужой записи по id (IDOR) | Фильтр видимости прямо в SQL-запросе, ответ «не найдено». |
| CSRF | Server Actions проверяют Origin, плюс `SameSite=Lax`. |
| XSS | Экранирование React, проверка ссылок, заголовки CSP, `X-Frame-Options: DENY`, `nosniff`, `Referrer-Policy`, HSTS в production. |
| SQL-инъекции | Только параметризованные запросы (Drizzle). |
| Утечка секретов | Секреты только в переменных окружения, `.env` в `.gitignore`. В логах нет паролей и персональных данных. |
| Подчистка следов | Журнал защищён от изменения триггером базы. |

### 9.2 Требуется до работы с реальными данными
- HTTPS/TLS на сервере; шифрование данных при хранении.
- MFA (TOTP или корпоративный SSO).
- Приватное файловое хранилище, короткоживущие подписанные ссылки, ограничения типа и размера файлов, антивирусная проверка.
- OAuth-токены шифруются (AES-256-GCM, ключ в env), их можно ротировать.
- Резервное копирование и регулярная проверка восстановления.
- Смена или удаление демо-пользователей.

## 12. Интеграция с Google Calendar (план, Sprint 2b)

1. В тестовом проекте Google Cloud создаётся OAuth Client с redirect URI `/api/integrations/google/callback`.
2. `GOOGLE_CLIENT_ID` и `GOOGLE_CLIENT_SECRET` хранятся только в серверных переменных окружения.
3. Подключение идёт по OAuth с `state` и PKCE и минимальным scope `calendar.events`.
4. Refresh-token шифруется и хранится в `integrations`. Пароль Google приложение не получает никогда.
5. Изменения из EXECUTIVE AI отправляются в Google; входящие изменения приходят через `syncToken`.
6. Ошибки синхронизации показываются в интерфейсе.
7. Пока интеграция не подключена и не проверена, интерфейс честно показывает «Не подключено».

## 17. Правила разработки (для Claude Code)

1. Работать поэтапно, не реализовывать всё сразу. После каждого этапа запускать `npm run typecheck && npm test && npm run build` и показывать, что сделано и что осталось.
2. Объяснять действия простым языком, по-русски.
3. Ключи, OAuth secrets и пароли — только в переменных окружения. Не помещать их во frontend, Git или исходный код и не просить вставлять их в чат.
4. Использовать только вымышленные данные.
5. Каждое AI-действие должно давать проверяемый результат и иметь ручной вариант.
6. Финансовые вычисления — только детерминированным кодом.
7. Критичные действия выполняются только после подтверждения.
8. Права проверяются на сервере. На каждое новое право — тест обхода роли в `tests/rbac.test.ts`.
9. Не утверждать, что интеграция работает, пока она не подключена и не проверена.
10. Если действие небезопасно или требует согласования, оставить безопасную заглушку и объяснить, что мешает.
11. Не создавать фиктивные кнопки, интеграции и цифры ради демонстрации.
12. Next.js 16: `middleware` называется `proxy` (`src/proxy.ts`); `params`, `searchParams` и `cookies()` — асинхронные.
